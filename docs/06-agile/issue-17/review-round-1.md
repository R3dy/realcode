## Comments

### 1-C1 — Prove the Skill invocation path works in the sandbox at runtime, or fail loud when it can't
**Plan section:** §3 (Integrations), §4.5, §10
**Problem:** The plan's core mechanism — "the agent invokes the anymake skill via the Skill tool" with content "loaded at runtime" through the opencode config mount (`runner.ts:194-198`, verified present) — has never been observed working. Across every historical sandbox run (`data/runs/*/containers/*.log`), the only tools ever invoked are `bash`, `read`, `edit`, `glob`, `grep`, and `todowrite`; there is not a single `skill` tool_use event, even though `frame.yaml`, `discover.yaml`, `spec.yaml`, and `change.yaml` already instruct agents to use the Skill tool. In `run_fe2c6d9e`'s discover stage, the agent text says "Let me load the skill first as instructed" — and no skill call follows it; two `read` calls are all that happen. The known historical fact is asymmetric in the wrong direction: ADR-009 established that `run --auto` lacks the *Task* tool; nothing anywhere establishes that it *has* the Skill tool. Root causes for skill absence could include the plugin never loading in the sandbox (opencode resolves the git-URL plugin entries in the mounted `opencode.json` by cloning from GitHub; only `~/.config/opencode` is mounted — there is no `~/.cache/opencode` plugin-cache mount and every spawn is `docker run --rm`, so each spawn needs working egress to github.com plus clone time, or a preinstalled plugin in `Dockerfile.sandbox`), or `run --auto` mode simply not registering the skill tool. Either way: the plan's fallback clauses convert failure into *silent parametric recall* — every grep test in §10 passes while the pipeline wraps nothing, which is issue #17's disease recreated one layer down.
**Required change:** (1) Add a designed verification step to §10: a smoke dispatch (can be a documented manual verification plus, ideally, a scripted check) that spawns one sandbox with the mounted config and a trivial prompt, and asserts from the `--format json` event stream that a `skill` tool_use occurred and returned anymake content — failing the story if absent. (2) In §4.5, name the plugin-resolution path in the sandbox explicitly (git clone at spawn vs. cache mount vs. preinstall in `Dockerfile.sandbox`) and which one this plan relies on; if the chosen answer needs engine/image changes (e.g., a plugin-cache mount), say so — the current "no Dockerfile or package.json changes needed" claim is unverified. (3) Decide the unavailable-Skill behavior and encode it: with the silent fallback the drift is undetectable, so either make the missing-Skill case escalate loudly, or state the fallback is temporary until the smoke check stands as the guard — and say which, with a criterion.

### 1-C2 — §4.2's "Every pipeline-stage spec already has the `Skill` tool in its `tool_allowlist`" is false; the rewrite leaves plan.yaml and ship.yaml self-contradictory
**Plan section:** §4.2, §9 (A17.1 criteria 1, 3)
**Problem:** `plan.yaml`'s `tool_allowlist` is `[Read, Write, Edit, Bash, WebFetch]` — no `Skill`. `ship.yaml`'s is `[Read, Write, Bash]`, its prompt asserts "You have ONLY Read, Write, and Bash. Do NOT invoke skills" (lines 13-14), and its header documents this as deliberate: "Self-contained for headless opencode: NO skill invocation (tool set is Read/Write/Bash only)" (line 2). No A17.1 criterion touches `tool_allowlist`, so after the rewrite both files contradict themselves (prompt says use Skill; declared tool set says it doesn't exist). Two related facts the plan should record rather than lean around: (i) `tool_allowlist` is parsed (`src/agents/spec-loader.ts:10`) but **never enforced** — `buildDispatchMessage` (`src/agents/runner.ts:459-486`) puts only `permission_mode` in the prompt text and `runner.ts:296-303` passes no tool-restriction flags to opencode — so "already in the allowlist" is not evidence of availability, and ADR-001's "tool allowlist enforced at the opencode level" is aspirational; (ii) `ship.yaml`'s no-skill fast path is a deliberate design (3 bash calls max, trusts build-stage test results, `permission_mode: unattended_with_approval_on_deploy`), and converting the ship stage to open-ended anymake Phase 5 skill invocation changes its speed and determinism — the plan offers uniformity as the only rationale.
**Required change:** Correct §4.2's claim. Add to A17.1: (a) update `plan.yaml`'s `tool_allowlist` to include `Skill`; (b) for `ship.yaml`, either add `Skill` to the allowlist **and** rewrite the "You have ONLY Read, Write, and Bash. Do NOT invoke skills" lines and header comment, with a one-sentence rationale for why the deliberate fast path is being changed — or explicitly scope ship *out* of the Skill delegation (keep it self-contained by design, just keep the traversal guard and remove nothing) and record that exception in ADR-012/§6. Either resolution is acceptable; silently landing a self-contradictory spec is not.

### 1-C3 — `build.yaml` missed: the grep-zero acceptance criterion is unachievable as scoped
**Plan section:** §3 (Modules), §8, §9 (A17.1), §10
**Problem:** "Do NOT read or search for any anymake docs" appears in **three** spec files, not two: `worker.yaml` (51-53), `validator.yaml` (40-41), and `build.yaml` (39-41). The plan's module list and criteria cover worker/validator only. A17.1's final criterion ("No spec contains 'Do NOT read or search for any anymake docs'. Grep returns empty.") therefore fails against `build.yaml`. `build.yaml` also carries a second anymake clause the §10 greps don't catch: lines 99-100, "Do not invoke anymake skills as a dispatch mechanism — reading their docs as reference is fine, dispatching is not." Verified `build.yaml` is dead config: nothing in `src/` references it (grep for "build.yaml" in `src/` → zero hits) and `stage-graph.yaml`'s build stage declares `inner_loop: anymake-build-loop` + `worker_spec` + `validator_spec` but no `agent_spec`. Its header (lines 3-4) even documents the superseded A4.3 single-session model that ADR-009 replaced.
**Required change:** Add an A17.1 (or A17.2) criterion: "Delete `agent-specs/build.yaml` — dead config, unreferenced by `stage-graph.yaml` and `src/`; superseded by the ADR-009 engine-orchestrated worker/validator specs." Add `build.yaml` to §3's module list and to §8's blast radius. If the architect prefers tombstoning over deletion, say so explicitly and adjust the two grep tests to exclude it — but deletion is cleaner and matches ADR-012.

### 1-C4 — §10's regression list omits the test files pinned to the specs being edited
**Plan section:** §10
**Problem:** §10 names `tests/agents.test.ts`, `tests/engine/*`, `tests/dashboard-*` as the unchanged regression set but omits `tests/agent-specs/worker-validator-specs.test.ts` — the file that pins the exact tokens this rewrite must preserve in worker/validator: the traversal guard (`node_modules`, `.git`, `dist`, `coverage`), "NO Task tool", `NEVER edit`, and the gate_verdict/verdict contract phrases (lines 38-55, 108-123, 69-80, 134-144). These tests *will* still pass if the worker/validator edits only remove the anymake-read sentence (verified: the INV-7 regexes only forbid positive instructions like `Read PHASE_GUIDES`; negative mentions are allowed, and nothing pins the anymake sentence itself) — but that compatibility is a claim the plan never checks or names, and this test file is precisely the one that catches a sloppy worker/validator rewrite. `tests/agents.test.ts` (loads `frame.yaml` and asserts its shape, lines 30+) belongs in the named list explicitly for the same reason.
**Required change:** Extend §10's regression list to name `tests/agent-specs/worker-validator-specs.test.ts` and `tests/agents.test.ts`, with the note that A17.1's worker/validator criteria must preserve the pinned tokens (traversal guard, "NO Task tool", "NEVER edit", gate_verdict phrases).

## Verdict

**VERDICT: NEEDS CHANGES** — comments 1-C1…1-C4 must be resolved; architect revises and resubmits for round 2.

**Summary:** The diagnosis is sound and unusually well-evidenced — every file:line citation I checked (plan.yaml:14-42, worker.yaml:51-53, runner.ts:194-198, ADR-006/009, INV-7, D-7) held up, the intent-conflict handling is correct, and the scope is disciplined. But the plan builds its entire fix on an unverified premise — that the Skill tool works inside sandbox `opencode run --auto` — which the full run history contradicts (zero skill invocations ever, including by a discover agent that announced it was invoking one), and whose silent fallback recreates the exact drift the issue exists to kill. Add a runtime smoke proof (1-C1), fix the allowlist/ship staging facts (1-C2), delete or tombstone the dead `build.yaml` that breaks the grep-zero criterion (1-C3), and name the spec-pinned regression tests (1-C4); this is otherwise close to approval.
