Additionally, `tests/integration/security.test.ts` iterates `graph.stages` calling `loadAgentSpec(path.resolve(REPO_ROOT, stage.agent_spec))` (tool-allowlist tests) and reads `buildStage.agent_spec` directly ("the build stage includes Edit + Bash") — the plan breaks this suite too, and §8's blast-radius table never mentions it. (Note also: the blanket assertion "every AgentSpec… `toContain('Write')`" would fail for the new `validator.yaml`, whose Read+Bash-only allowlist is *correct* for a validator — the test needs updating, not the spec.)
**Required change:** (a) In §4.1 and A4.1: make `agent_spec` optional in the `StageEntry` schema and add a `validateGraph()` rule — exactly one of `agent_spec` XOR (`inner_loop` + `worker_spec` + `validator_spec`) must be present, with all referenced paths resolving. (b) Add to §8: `tests/integration/security.test.ts` is in the blast radius; the tool-allowlist tests must be extended to load `worker_spec`/`validator_spec` for inner-loop stages (asserting worker has Read/Write/Edit/Bash, validator has Read+Bash and no Write), and the `buildStage.agent_spec` assertion must be repointed. (c) Add the updated security tests to §10.

### 1-C2 — `specOverride` is under-specified: schema lookup and per-story template context have no mechanism
**Plan section:** §4.2, §4.3, Stories A4.2/A4.4
**Problem:** Two mechanical gaps make the plan's core dispatch path fail as written.
(1) *Schema lookup:* `AgentStageRunner.run()` validates the extracted artifact with `STAGE_SCHEMAS[stage.id]` (`src/agents/runner.ts:109`) and builds the prompt's schema JSON via `getStageSchemaJson(stage.id)` (lines 59, 299–303). When `BuildLoopRunner` dispatches a worker with `specOverride`, the `stage` argument is still the build `StageEntry` (`id: "build"`) — so a `WorkerOutput` artifact gets validated against `BuildOutput` (guaranteed `safeParse` failure → escalate) and the worker's prompt shows the wrong output schema. Registering `build_worker`/`build_validator` in `STAGE_SCHEMAS` (§4.3) changes nothing unless the lookup key switches — e.g., to the loaded spec's `stage:` field (`worker.yaml` declares `stage: build_worker`). The plan never specifies this.
(2) *Template context:* the worker/validator templates use `{story_id}`, `{story_title}`, `{acceptance_criteria}`, `{worker_output}` — but `fillTemplate()` only sees `gatherPriorArtifacts()` output (runner.ts:57–58), which has no story fields; unresolved placeholders pass through *literally* (runner.ts:199 `return match`), so the worker agent would receive a prompt containing the literal string `{story_id}`. The plan specifies only a `specOverride` parameter; no extra-context parameter exists.
**Required change:** Specify the full `AgentStageRunner.run()` signature change — e.g. `run(item, stage, workspacePath, opts?: { specOverride?: string; schemaKey?: string; extraContext?: Record<string, unknown> })` — where schema selection and `getStageSchemaJson` use `schemaKey ?? stage.id` (or derive the key from the overridden spec's `stage:` field), and `extraContext` is merged into the `fillTemplate` context. Update the A4.2/A4.4 acceptance criteria to match, and state where `{acceptance_criteria}` is serialized (array → joined string) before interpolation.

### 1-C3 — Worker/Validator output contracts don't map onto the BuildLoopRunner control flow
**Plan section:** §4.2 (pseudocode) vs §4.3/§4.8/§4.9 (contracts) vs A4.2 (criteria)
**Problem:** `AgentStageRunner.run()` returns `output_status = validated.data.gate_verdict`, and `StageOutputBase.gate_verdict` is `z.enum(["pass", "needs_changes", "escalate"])` (`src/schemas/base.ts:14`). Three contradictions follow:
(1) §4.2's pseudocode branches on `validatorResult.output_status == "fail"` — a value that can never occur. A validator FAIL must arrive either as `gate_verdict: "needs_changes"` or as `gate_verdict: "pass"` with `artifact.verdict: "fail"`; the plan's `validator.yaml` contract says `gate_verdict: "pass" | "escalate"` and carries the verdict in `artifact.verdict` — but then §4.2 must read `artifact.verdict`, not `output_status`. It doesn't.
(2) The `worker.yaml` contract offers only `gate_verdict: "pass" | "escalate"` — there is no defined gate_verdict for the *retryable failure* case (`result: "failed"`, `failure_type: "environment"`), which A4.2 says must trigger a worker retry. §4.2's pseudocode doesn't handle worker failure at all (only worker escalate).
(3) §4.2 retries a worker *escalation* up to 3 times (`if workerResult.output_status == "escalate": … continue`), while A4.2 says "on Validator `escalate`, escalate immediately" and planning-ADR-007's retry matrix says escalation → stop, surface to user. The three sections disagree on the same state machine.
**Required change:** Add an explicit mapping table to §4.2: every combination of worker `artifact.result`/`failure_type` and validator `artifact.verdict`/`escalation_type` → BuildLoopRunner action (retry worker / escalate story / proceed), with the exact `gate_verdict` each spec must emit for each case; make `worker.yaml` and `validator.yaml` output contracts emit those values; rewrite the pseudocode to branch on the artifact fields it actually receives; reconcile with ADR-007's retry matrix (state explicitly where the plan deviates — e.g. "implementation failure escalates immediately rather than ADR-007's max-1 re-dispatch" — and why).

### 1-C4 — LiveTraceStream has no data source: no per-turn/agent spans exist in Phoenix, and the plan creates no emitter
**Plan section:** §4.10, §4.11, Story A4.5 (Experience Script)
**Problem:** Issue requirement #4 is "real-time agent messages + tool calls from the Phoenix traces." The plan's SSE endpoint filters Phoenix spans by `attributes['realcode.run_id'] == '<id>'` and renders "agent messages + tool calls" from them. But: (1) the only spans the system emits are engine-side run/stage spans (`tracing.ts`; `dispatcher.ts:216` calls `startStageSpan`) — `startTurnSpan`/`recordTokenUsage` are defined but **never called anywhere** (grep-verified); stage spans carry no agent messages or tool calls. (2) The plan's new `build_worker`/`build_validator` spans (§4.10) are still engine spans — no message/tool content. (3) Nothing pipes the sandbox's opencode telemetry to Phoenix: `runDocker()` passes only `OTEL_TRACEPARENT`, `OPENCODE_MODEL`, and model keys (`sandbox/runner.ts:77-79`) — no `OTEL_EXPORTER_OTLP_ENDPOINT`; the sandbox runs on `realcode-sandbox-net` while Phoenix is on `realcode-net` (docker-compose.yml defines only `realcode-net`; the sandbox network is external), so even a configured exporter couldn't resolve `phoenix:6006`; and opencode-emitted spans would not carry the `realcode.run_id` attribute the GraphQL filter requires. As specified, LiveTraceStream renders stage-start/stage-end events only — A4.5's Experience Script ("LiveTraceStream shows real-time agent messages + tool calls streaming from Phoenix") cannot pass.
**Required change:** Choose and specify one mechanism: (a) *engine-side synthesis* — `BuildLoopRunner` (or `AgentStageRunner`) converts each sandbox's parsed `jsonEvents` (already captured in `SandboxResult`) into per-turn OTel spans/events stamped with `realcode.run_id`, `realcode.story_id`, agent name, tool-call attributes — this works with the existing exporter and filter, but is only "real-time" per completed sandbox unless the runner streams events during execution (if streaming is required, say how: tail the child's stdout incrementally instead of buffering to exit); or (b) *sandbox-side export* — pass `OTEL_EXPORTER_OTLP_ENDPOINT` into the sandbox, put sandboxes on a network that reaches Phoenix, and provide evidence that headless opencode emits OTLP spans with propagatable custom attributes (the ADR-001 spike documented tool calls in the *JSON event stream*, not OTel). Either way, state exactly which span attributes the §4.11 GraphQL query filters on, and fix or justify the `realcode-sandbox-net` vs `realcode-net` reachability. If the chosen mechanism can't deliver mid-execution messages, say so and scope LiveTraceStream to per-completed-sandbox turns (with container logs as the truly-live stream).

### 1-C5 — Host-path translation for the new mounts is broken as specified (Docker-in-Docker)
**Plan section:** §4.6, §4.12, Story A4.3
**Problem:** The engine runs *inside* a container where `MISSION_CONTROL_ROOT=/mission-control` (docker-compose.yml:32). §4.6 has the engine pass `-v ${MISSION_CONTROL_ROOT}:${MISSION_CONTROL_ROOT}:ro` to each sandbox's `docker run` — but for sibling-container spawns, Docker resolves bind-mount **sources on the host**, and the host has no `/mission-control`; Docker will auto-create an empty dir there and the sandbox silently gets an empty mount, so every MCP server under mission-control (e.g. realmemory's `dist/bin.js`) fails to start. The same class of bug hits `REALCODE_OPENCODE_CONFIG_DIR`: the engine needs the **host** path to hand to `docker run -v`, but also needs a **container-local** path to read `opencode.json` for `discoverMcpPaths()` — the plan's compose mounts the config at `/root/.config/opencode` on the engine while the env var points at the host path, so `discoverMcpPaths(process.env.REALCODE_OPENCODE_CONFIG_DIR)` reads a path that doesn't exist inside the engine container. The codebase already solves exactly this problem for workspaces via `REALCODE_HOST_DATA_DIR` path translation (`sandbox/runner.ts:65-69`) — the plan doesn't reuse the pattern. Additionally: `REALCODE_OPERATOR_HOME` is introduced in §4.12/A4.3 but never used anywhere in the plan.
**Required change:** Mirror the existing pattern: introduce explicit host-path env vars (e.g. `REALCODE_HOST_MISSION_CONTROL_ROOT=/home/royce/mission-control`, `REALCODE_HOST_OPENCODE_CONFIG_DIR=/home/royce/.config/opencode`) used for `docker run -v <host>:<same-host-path>:ro` sandbox mounts, while the engine reads its own container-local mounts (`/mission-control`, `/root/.config/opencode`) for discovery. Update the §4.6 mount list, the §4.12 compose YAML (which must also keep the existing `/mission-control` mount for `seedWorkspaceFromProject`), and the A4.3 criteria. Either use `REALCODE_OPERATOR_HOME` or delete it from the plan.

### 1-C6 — Security: the opencode-config/MCP mount is a secret-handling and trust-boundary surface treated in one sentence
**Plan section:** §4.6 (design), §6 (ADR-003 row), §10 (no security tests), Story A4.3
**Problem:** The plan mounts the operator's entire opencode config directory into every sandbox container. Verified facts: the mount is specified read-only; today's `opencode.json` contains no key-like values (two local MCP server definitions only); model API keys reach the sandbox via env through `collectModelEnv()` (pre-existing, covered by `security.test.ts`). But the plan does not address: (1) *future/config-drift secret exposure* — the whole directory is mounted (including `agent/`, `skills/`, `node_modules/`, and anything ever added), and MCP server configs commonly carry API keys or connection strings; planning-ADR-003's hard gate is "**no real secret is ever mounted** into a sandbox" and the agentic-harness manifest's gate delta #3 plus "Keep: heightened — no secrets in any mounted volume" apply; the plan adds no scan/warn/refuse safeguard. (2) *MCP trust boundary* — a sandboxed agent with Bash can invoke the mounted MCP servers: realmemory exposes store/update/forget (write access to the operator's cross-project memory store) and codebase-memory indexes all projects; the sandbox agent can also simply `cat /root/.config/opencode/opencode.json`. This may be entirely acceptable for a single-operator personal tool — the reporter explicitly requested this inheritance in the issue — but the plan must say so explicitly, not silently. (3) There is no security verification anywhere in §10 for the new surface (e.g. asserting the mount is `:ro`, asserting `discoverMcpPaths` output contains no secret-pattern values).
**Required change:** Add a Security section (or a §4.6 subsection) that: documents the trust boundary being crossed (operator config + MCP servers with write-capable memory tools are reachable from LLM-directed sandboxed code); adds an engine startup check that scans the mounted config (at minimum `opencode.json`) for key/token/secret-pattern values and refuses or loudly warns; considers mounting only the needed subpaths (`opencode.json`, `agent/`, `skills/`) rather than the whole directory; and records that the reporter explicitly requested this mechanism in issue #4. Extend §10 with security tests: config mount is read-only, and the startup secret-scan fires on a seeded key-containing fixture. Finally, add to §6/§11 the note required by the arbiter: this plan is security-relevant (secrets surface), so **final approval is the real user's in every mode** — the approval gate must not be the Product Owner Proxy.

### 1-C9 — Lease/timeout model for the inner loop is undecided, and the gestured fix is insufficient
**Plan section:** §8 (queue/lease row), A4.2 (lease criterion)
**Problem:** The lease default is 10 minutes (`sqlite-queue.ts:6`, `LEASE_DEFAULT_MS`), and `dispatchCycle()` claims without passing `lease_ms` (`dispatcher.ts:193`). A 17-story inner loop (the issue's own example) runs far longer than even §8's proposed "long lease (e.g. 30 min)". On expiry, `expire_leases()` clears `worker_id`/`lease_expires_at` and increments `retry_count` — and since the work_item's status stays `specified` (an eligible state), the **next dispatchCycle re-claims it and starts a second `BuildLoopRunner`** for the same run: double spend, two concurrent writers of `build-state.json`, duplicate containers. The plan's proposed mitigations don't work: `queue.annotate()` is a no-op in the SQLite implementation (`sqlite-queue.ts:76`) and doesn't touch leases; "or re-claims" is unspecified; "30 min" is shorter than realistic loops. The plan also never specifies (a) the per-sandbox `timeoutMs` for worker/validator dispatches (does each of 34 sandboxes get the stage's full `timeout_ms: 1200000`? that's an 11-hour ceiling), or (b) any overall wall-clock bound for the inner loop. §8 names the risk but the "Protection" column is an undecided OR-list, and §10 has no test for it.
**Required change:** Decide and specify: (1) the lease mechanism — either the dispatcher passes `lease_ms` derived from the stage (requires changing the `claim()` call at `dispatcher.ts:193`), or `BuildLoopRunner` heartbeats the lease between stories via a *real* queue method (add one to the `Queue` interface + SQLite impl); state which. (2) The per-sandbox timeout for worker/validator dispatches (a new optional graph field, or a fraction of `stage.timeout_ms` — pick one). (3) An overall inner-loop wall-clock bound and what happens when it's hit. (4) A regression test in §10: a build whose inner loop exceeds the old 10-min default completes without a second dispatch of the same work_item.

### 1-C10 — §7 prescribes the ux-design.md token *names*; the as-built code renamed the palette (`slate-*` → `ink-*`)

### 1-C11 — §4.4's `backlog_md` fallback parser is half-specified, and its output can't satisfy `StorySpec`
**Plan section:** §4.4, A4.2 (fallback criterion)
**Problem:** The fallback "extracts story IDs + titles from the markdown headings" — but `StorySpec` requires `acceptance_criteria: z.array(z.string().min(1)).min(1)`, and `depends_on[]` drives `nextReadyStory()`'s dependency ordering. A fallback that produces ids+titles only yields stories with empty acceptance criteria (which would fail schema validation if `stories[]` is validated on write, and leaves the Validator with nothing to check) and no dependency edges (destroying the ordered-build guarantee the whole change exists to provide — run_0ba334d1's backlog had dependencies). No parse format is specified (which heading level? what AC syntax?), so A4.2's "falls back to parsing `backlog_md`" criterion is untestable. Meanwhile the plan already updates `agent-specs/spec.yaml` to emit structured `stories` for every new run, so the fallback only serves legacy artifacts — of which there are essentially none worth preserving post-launch of this change.
**Required change:** Pick one and write it down: (a) **drop the fallback** — make `stories` required (validate `story_count === stories.length` with a zod `.refine()`, which §4.4 states as a rule but never assigns an enforcement point), and have `BuildLoopRunner` escalate with a clear error on a spec artifact lacking `stories`; or (b) fully specify the fallback parser (heading regex, AC extraction, `depends_on` extraction) with fixtures and tests in §10. Option (a) is recommended — it's less code and this repo controls the only spec producer.

## Verdict

**VERDICT: NEEDS CHANGES** — comments 1-C1…1-C12 must be resolved; architect revises and resubmits for round 2.

**Summary:** The plan's root-cause analysis is accurate and fully verified against the code at 9faa3cf, and the overall architecture (engine-orchestrated serial Worker/Validator loop, per-story state file, dashboard mission-control section) is the right shape for the issue. But as written it cannot be built or approved: removing `agent_spec` from the build stage breaks engine startup and the existing security test suite (1-C1); the `specOverride` mechanism omits the schema-lookup switch and per-story template context, so every worker dispatch would validate against the wrong schema and receive literal `{story_id}` placeholders (1-C2); the Worker/Validator output contracts don't map onto the loop's control flow (1-C3); the headline Phoenix live-trace feature has no span emitter and no network path as specified (1-C4); the new sandbox mounts confuse host and container paths so MCP inheritance silently fails (1-C5); and the operator-config/MCP mount is a real secret-handling and trust-boundary surface the plan treats in one sentence (1-C6) — final approval for this plan must rest with the real user per the arbiter's security rule. Intent-layer citation hygiene (1-C7), blast-radius omissions (1-C8), the undecided lease model (1-C9), wrong design-token names (1-C10), the half-specified fallback parser (1-C11), and internal inconsistencies (1-C12) round out the required changes.
