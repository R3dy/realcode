## Comments *(required for every FAIL — each specific and actionable)*

### 2-C1 — The "existing e2e test still passes" claim is false three ways, and the `Engine` constructor change has unnamed consumers
**Plan section:** §8 (non-build-stages row), A4.1 (last criterion), A4.6 ("existing e2e test still passes"), §10 (regression line); wiring in §4.2
**Problem:** The plan asserts in four places that `tests/integration/e2e.test.ts` passes unchanged. It cannot:
1. **Mock spec artifact fails the new required field.** The e2e drives a run from intake to `shipped` through six real `dispatchCycle()` calls (`e2e.test.ts:158-181`). Its canned spec artifact (`STAGE_ARTIFACTS.spec`, lines 60–72) is `{ epics_md, backlog_md, dependency_graph, story_count: 8 }` — no `stories` array. Under §4.4's required `stories: z.array(StorySpec).min(1)`, `SpecOutput` validation fails → the spec stage returns `output_status: "escalate"` → the run escalates at spec and the `stageSequence` assertion (`framed, discovered, planned, specified, built, shipped`) fails.
2. **The e2e `Engine` has no `BuildLoopRunner`.** The test constructs `new Engine(graph, queue, storage, runner, tmpDir)` (line 151). With the graph's build stage now carrying `inner_loop`, the dispatcher's new branch (`stage.inner_loop ? await this.buildLoopRunner!.run(...) : …`) dereferences undefined at the build stage → caught by the dispatcher's try/catch → run escalated.
3. **The mock sandbox can't answer worker/validator dispatches even if a runner were wired.** `makeMockSandbox` keys its canned artifact off `Stage:\s*(\w+)` in the dispatch message (line ~113), and `buildDispatchMessage` stamps `Stage: ${stage.id}` (`runner.ts:315`) — which stays `build` under `specOverride`. A worker dispatch would receive the canned *BuildOutput* artifact and fail `WorkerOutput` validation → escalate.

The same wiring change hits the other `Engine` constructor call sites, none named in §8: `src/cli/index.ts:34` (the CLI entry point — its dispatch path would crash at the build stage exactly as in the e2e) and `security.test.ts:166/187`. As written, the 6-arg form `new Engine(graph, queue, storage, runner, buildLoop, DATA_DIR)` is positional, so all four 5-arg call sites fail typecheck (`tsc --noEmit` is a repo script) before any test runs.
**Required change:** (a) Decide the constructor mechanics and name every call site: either make the `BuildLoopRunner` parameter optional (and state what the dispatcher does when an inner-loop stage is reached with no runner configured — escalate with a clear error, never crash) or make it required and list `engine-loop.ts:27`, `src/cli/index.ts:34`, `e2e.test.ts:151`, and `security.test.ts:166/187` as call sites to update. Add `src/cli/index.ts` to §8's blast-radius table. (b) Specify the e2e update: the canned spec artifact gains a valid `stories` array satisfying the `.refine()`; the e2e `Engine` gains a `BuildLoopRunner` (either a real one wrapping the mock-sandbox `AgentStageRunner` with canned `WorkerOutput`/`ValidatorOutput` artifacts and a mock that distinguishes worker vs validator dispatches — e.g. keyed on a marker the plan adds to the dispatch message — or a stub `BuildLoopRunner` returning the canned build artifact; pick one and say so). (c) Reword the four "still passes" claims to "updated in story A4.X and passes," with the update assigned to a specific story's criteria.

### 2-C2 — §4.2's mid-loop-pause return path describes end states the transition table cannot produce
**Plan section:** §4.2 (control-doc block + pseudocode), §8 (control-doc row), A4.2 (pause criterion), A4.6 (control-doc test)
**Problem:** §4.2 says that on an operator pause mid-loop the runner "returns `{ output_status: "escalate", … }` so the dispatcher transitions the run to `paused_cost_cap` **or** leaves it `specified` (pending resume)." Mechanically, neither happens: `applyTransition(graph, "build", "specified", "escalate")` resolves to `escalated` (stage-graph.yaml: `{ from: specified, on: escalate, to: escalated }`), and `queue.release(item.id, "escalated")` is terminal — `claim()`'s safety net (`sqlite-queue.ts:44`) filters out `escalated`, so the work_item can never be re-claimed and the run cannot resume. The "or" is residual draft indecision of exactly the kind 1-C12 removed elsewhere, and it's about a product-visible behavior: does pausing a build mid-loop kill the run or suspend it?
**Required change:** Decide one and specify the mechanics: (a) **pause mid-loop = terminal escalation** — delete the "pending resume" language, state that the run ends `escalated` with `gate_notes` explaining the operator pause, and make the A4.2 criterion and the A4.6/§10 control-doc test assert `escalated` (not "exits cleanly" into an undefined state); or (b) **pause mid-loop = resumable suspension** — specify how, noting the dispatcher currently *always* applies a transition and releases the item after `runner.run()` returns: e.g. `BuildLoopRunner` returns a distinguished result (or throws a typed `PauseSignal`) that `dispatchCycle()` special-cases to release the work_item back to `specified` without firing a transition or counting a revision, plus a control-doc update. Either way, make §4.2's prose, pseudocode, §8's row, and the A4.2/A4.6 criteria say the same thing.

### 2-C3 — The lease heartbeat interval is shorter than the worst-case story cycle, so the double-dispatch race survives the fix designed to close it
**Plan section:** §4.13 (lease mechanism), §4.2 (pseudocode heartbeat placement), §8 (lease row), §10 (`lease-heartbeat.test.ts`)
**Problem:** §4.13 sets per-sandbox timeout = `stage.timeout_ms` (20 min) for *both* the Worker and the Validator, so one story can legitimately run 40 min. But the heartbeat fires only *before each story's Worker dispatch* (§4.2 pseudocode) with `lease_ms = stage.timeout_ms` — the lease expires 20 minutes into a worst-case story, mid-Validator. `expire_leases()` (verified at `sqlite-queue.ts:96-116`) then clears `worker_id`/`lease_expires_at`, leaves status `specified` (first expiry: `retry_count` 0→1, below the escalate threshold), and the next `dispatchCycle()` re-claims the item and starts a **second `BuildLoopRunner`** for the same run — the exact double-spend/duplicate-container/two-`build-state.json`-writers outcome 1-C9 demanded be closed. The §10 test as specified can't catch it: with instant mock sandboxes the loop finishes in milliseconds, so `expire_leases` never fires mid-story; the test only asserts `heartbeat` was called.
**Required change:** Make the lease outlast the maximum gap between heartbeats: either pass `2 × stage.timeout_ms` (plus margin) as the heartbeat `lease_ms`, or heartbeat again between the Worker and Validator dispatches — state which, and update §4.13's text, §8's protection column, and the A4.2 criterion to match. Strengthen the §10 lease test to exercise the real bound (e.g. fake timers where Worker and Validator each run a full `stage.timeout_ms` and `expire_leases` is asserted to never clear the lease mid-story), not merely that `heartbeat` was invoked.
