### 3-C1 — A4.1 lands a `stage-graph.yaml` edit that references files A4.4 creates, making the graph unloadable and A4.1's own "security.test.ts passing at A4.1" claim false
**Plan section:** §9 Story A4.1 (criteria: `stage-graph.yaml` edit, `validateGraph` XOR, `security.test.ts` update, last criterion's greenness claim) vs §9 Story A4.4 (first two criteria); §4.1 (XOR validation code); §8 (`security.test.ts` row); §10 (story attribution)
**Problem:** A4.1's criteria land three things simultaneously: (a) the `stage-graph.yaml` build-stage edit adding `worker_spec: agent-specs/worker.yaml` + `validator_spec: agent-specs/validator.yaml` and removing `agent_spec`; (b) the `validateGraph()` XOR rule whose code (§4.1, lines 87-98) requires both spec paths to **exist on disk** (`fs.existsSync` → `errors.push` → `GraphValidationError`); (c) the updated `security.test.ts`, whose tool-allowlist loop calls `loadAgentSpec(worker_spec)`/`loadAgentSpec(validator_spec)` and asserts their final allowlists (worker has Read/Write/Edit/Bash; validator has Read+Bash and no Write). But "agent-specs/worker.yaml exists and is valid per `AgentSpecSchema`" is **A4.4's** first criterion — the files don't exist at A4.1. A4.1's own last criterion even admits this ("the build stage is broken until … A4.4 (worker/validator specs exist)") while simultaneously claiming "Non-build stages ARE unaffected (verified by `security.test.ts` tool-allowlist + XOR-rule assertions **passing at A4.1**)." That verification claim is mechanically false. Consequences at end-of-A4.1 as written:
1. `loadStageGraph(GRAPH_PATH)` throws `GraphValidationError` ("worker_spec path … does not exist") — so **every** graph-loading suite goes red, not just the e2e: `tests/engine.test.ts` (loads at lines 9, 18, 27, 39), `tests/agents.test.ts` (line 109), `tests/integration/security.test.ts` (lines 22, 84, 94, 102, 146 — including A4.1's own updated suite and its new XOR assertion, which can never execute because the load throws first), and the e2e (line 143).
2. The engine cannot boot (`src/engine-loop.ts:19`), so A4.1's own Experience Script ("`POST /api/runs` … progresses through frame→spec") is unrunnable.
3. Even if the graph loaded, the updated tool-allowlist assertions require the spec files' **final** contents (A4.4 deliverables), not stubs.

A Worker dispatched on A4.1 with the plan + brief cannot make A4.1's criteria pass without silently absorbing A4.4's core deliverable — at which point A4.4's "exists and is valid" criteria are pre-satisfied and its scope is wrong. This is the same defect class this plan has been failed on twice before (1-C1: `loadStageGraph` throws at startup; 2-C1: false "still passes" claims): a test-greenness claim that doesn't survive contact with the graph loader.
**Required change:** Pick one and restate the affected criteria, claims, and §10 story attributions to match:

- **(b) A4.4 owns the graph flip.** Move the `stage-graph.yaml` build-stage edit, the `validateGraph` XOR path-existence enforcement for worker/validator specs (the schema-field additions can stay in A4.1 — they're inert without the yaml edit), and the `security.test.ts` update from A4.1 to A4.4. Restate A4.1's last criterion: at A4.1 the graph is unchanged, so **all** existing suites stay green (including the e2e — the build stage still dispatches the old single sandbox until A4.4); the e2e goes red at A4.4 and is updated green in A4.6.

### 3-C2 — A4.6(e)'s updated sandbox-call-count arithmetic is wrong (22 → 21)
